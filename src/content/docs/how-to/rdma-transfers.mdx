---
title: Transferring Data with RDMA
description: Learn how to read and write values directly into registered memory with the synchronous Python client.
---

:::caution[Experimental Feature]
RDMA transfers were added in Valkey GLIDE 2.6.0 and are currently an experimental feature of the synchronous Python client. The API may change in future releases.
:::

RDMA transfers move a value directly between the server and client memory.
For how this works and when it helps, see [RDMA Transfers](/concepts/client-features/rdma/).

## Prerequisites

* Both client and server machines need: 
  * Linux on an EC2 instance with an EFA device.
  * [libfabric](https://ofiwg.github.io/libfabric/) 2.4 or a later 2.x version. On EC2 with EFA, the EFA installer provides it under `/opt/amazon/efa`. Set `GLIDE_LIBFABRIC_PATH` to the library file to use a copy GLIDE does not find on its own.
* The synchronous Python client, `valkey-glide-sync`. The published package includes RDMA support with an EFA direct provider.
* A Valkey server with the [valkey-large-object module](https://github.com/valkey-io/valkey-large-object) that serves the `BLOB.*` RDMA commands.
  * Note: the module's `max-object-size` (default 512 MiB) caps what `rdma_set` can store, so increase it if you need to store larger values.
* Check `ulimit -l` (or `LimitMEMLOCK=` in the systemd unit) is at least the total you will register with RDMA. Registration pins pages, so `RLIMIT_MEMLOCK` must cover every open region.
* Only to register GPU memory: the CUDA driver on the client machine, and a libfabric built with CUDA support.

## Check that RDMA can run

```python
from glide_sync import GlideClient

# does this build of GLIDE include RDMA?
GlideClient.rdma_available()

# does a compatible libfabric version load on this machine?
GlideClient.rdma_usable()
```

`rdma_usable()` does not look for fabric hardware, so creating a client with the EFA provider can still fail on a machine without an EFA device.

## Create a client with RDMA

Pass an `RdmaConfiguration` when creating the client:

```python
from glide_sync import (
    GlideClient,
    GlideClientConfiguration,
    NodeAddress,
    RdmaConfiguration,
    RdmaProvider,
)

config = GlideClientConfiguration(
    addresses=[NodeAddress("localhost", 6379)],
    rdma=RdmaConfiguration(provider=RdmaProvider.EfaDirect()),
)
client = GlideClient.create(config)
```

`GlideClusterClientConfiguration` takes the same `rdma` argument. `RdmaConfiguration` also accepts an `interface` to choose a fabric device when the machine has more than one. Without it, GLIDE uses the first domain it finds.

The client connects even if the server does not serve the RDMA commands, and ordinary commands keep working. The first transfer reports the missing server support.

## Register memory

Register a large block of memory once, then address windows of it for each transfer:

```python
slab = bytearray(64 << 20)  # or an mmap, a NumPy array, a tensor's storage
region = client.register_rdma_region(slab)

region.capacity               # 67108864
region.window(4096, 1024)     # 1 KiB starting 4 KiB in
region.window()               # the whole region
```

Any writable, C-contiguous, non-empty buffer works. GLIDE keeps a reference to it while the region is open and never copies or frees it.

## Register GPU memory

To have the server read and write CUDA GPU memory directly, with no copy through host memory, create the client with `device_memory=True`:

```python
import torch
from glide_sync import (
    GlideClient,
    GlideClientConfiguration,
    NodeAddress,
    RdmaConfiguration,
    RdmaProvider,
    RdmaSetChecksum,
)

config = GlideClientConfiguration(
    addresses=[NodeAddress("localhost", 6379)],
    rdma=RdmaConfiguration(provider=RdmaProvider.EfaDirect(), device_memory=True),
)
client = GlideClient.create(config)

tensor = torch.empty(64 << 20, dtype=torch.uint8, device="cuda")
region = client.register_rdma_region(tensor)

n = 1 << 20
tensor[:n].fill_(7)        # GPU work that writes the window
torch.cuda.synchronize()   # finish it before rdma_set

crc = your_gpu_crc32c(tensor[:n])  # your own CRC-32c, computed on the GPU
client.rdma_set(b"weights", region.window(0, n), checksum=RdmaSetChecksum.Known(crc))
# or checksum=RdmaSetChecksum.Skip()

receipt = client.rdma_get(b"weights", region.window(n, n))
if receipt is None:
    ...  # the key does not exist; nothing was written
else:
    # The bytes are in tensor[n : n + receipt.bytes_written].
    # GLIDE does not check them; compare your own CRC-32c with receipt.checksum.
    ...
```

* `register_rdma_region` accepts a CUDA `torch.Tensor`, a CuPy array, or any object whose `__dlpack_device__` names a CUDA device and that offers `__cuda_array_interface__`. For a tensor whose dtype has no typestr, such as float8, GLIDE uses `data_ptr()`. The memory must be writable and C-contiguous.
* Host memory registers the same way with or without `device_memory`.
* You can register GPU memory from any thread, including one that never used CUDA.
* A GPU region has no host view: `region.memoryview()` and `window.memoryview()` raise `RdmaError`. Read and write the data through the tensor or array.
* `rdma_set` on a GPU window takes `RdmaSetChecksum.Skip()` (the default) or `RdmaSetChecksum.Known(crc)`. `Compute()` raises `RdmaError` before anything is sent, and the region stays usable.
* `rdma_get` returns the server's CRC-32c in `receipt.checksum` without checking the landed bytes against it.
* Finish GPU work that writes a window before `rdma_set`, for example with `torch.cuda.synchronize()`. Don't touch a window with GPU work while a transfer of it runs. Submit GPU work that reads a window only after `rdma_get` returns. If the device's `CU_DEVICE_ATTRIBUTE_GPU_DIRECT_RDMA_WRITES_ORDERING` does not cover that work, call `cuFlushGPUDirectRDMAWrites` first.
* A tensor that requires grad can be registered, but `rdma_get` writes it outside PyTorch, so autograd's version counter does not change. Don't `rdma_get` into storage that a pending backward pass saved.
* If the tensor's address range, size or layout changes after registration (for example `resize_()` or `set_()`), the next transfer raises `RdmaError` before anything is sent. The region stays usable once the range is restored. Otherwise, close it and register again.
* Only CUDA device memory is supported. CUDA managed memory (`cudaMallocManaged`) and memory on other devices, such as ROCm, raise `TypeError` before anything is registered.
* Without `device_memory=True`, registering GPU memory raises `RdmaError`.
* If the provider doesn't offer GPU memory (FI_HMEM) on the host, creating the client fails with an error naming FI_HMEM. `EfaDirect` offers it on a GPU host whose libfabric was built with CUDA.
* The first GPU registration loads the CUDA driver, `libcuda.so.1`. If it can't be loaded, registration raises `RdmaError`.

:::note
A tensor from PyTorch's expandable segments (`PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True`) can span more than one mapping. Registering one that does needs libfabric 2.7.0 or later and the dmabuf path libfabric takes by default. On libfabric 2.6.0 such a registration fails in `fi_mr_regattr` with `Invalid argument`. GLIDE does not check the libfabric version for this.
:::

For how GPU transfers work, see [GPU memory](/concepts/client-features/rdma/#gpu-memory).

## Write a value

```python
from glide_sync import RdmaSetChecksum

window = region.window(0, 11)
window.memoryview()[:] = b"hello world"

client.rdma_set(b"greeting", window)
```

To have the server check the bytes it read before storing them, pass a checksum:

```python
# GLIDE computes the CRC-32c of the window.
client.rdma_set(b"greeting", window, checksum=RdmaSetChecksum.Compute())

# You already have it, so the window is not read again.
crc = GlideClient.rdma_checksum(window.memoryview())
client.rdma_set(b"greeting", window, checksum=RdmaSetChecksum.Known(crc))
```

If the bytes don't match, the server stores nothing and `rdma_set` raises `RdmaError`.

## Read a value

```python
receipt = client.rdma_get(b"greeting", region.window(4096, 4096))
if receipt is None:
    ...  # the key does not exist; nothing was written
else:
    value = region.window(4096, receipt.bytes_written).memoryview()
```

The value is in the window by the time `rdma_get` returns. For host memory, GLIDE has already checked it against the checksum the server sent. For GPU memory, see [Register GPU memory](/how-to/rdma-transfers/#register-gpu-memory).
A value larger than the window raises `RdmaError` without writing anything.

## Transfer from several threads

A region carries one transfer at a time; a second transfer through a busy region raises `RdmaError`.
To transfer from several threads at once, give each thread its own region, for example one per non-overlapping slice of the same buffer:

```python
view = memoryview(slab)
chunk = len(slab) // 4
regions = [
    client.register_rdma_region(view[i * chunk : (i + 1) * chunk])
    for i in range(4)
]
# Each thread transfers through its own region.
```

Make sure the slices don't overlap. GLIDE does not check that.

## Handle a failed transfer

Some failures leave the region usable, such as a value too large for its window or a checksum mismatch.
Others close it, because the server might still be using the memory, such as a lost connection.
The error's class doesn't tell you which, so check `region.closed` after any error:

```python
from glide_sync import GlideError

try:
    receipt = client.rdma_get(key, region.window(offset, length))
except GlideError:
    if region.closed and not client.closed:
        region = client.register_rdma_region(slab)
    raise
```

GLIDE never resends a transfer the server may have run. The cluster client re-sends a transfer the server refused without running it or that was never sent (e.g. MOVED, READONLY after a failover).

Registering the same memory again raises `RdmaError` while GLIDE still holds it. With EFA that only happens after a device error. `region.memory_released` tells you whether the memory is free.

## Cancel a transfer

Transfers have no timeout. To give up on one, close the client from another thread:

```python
import threading

timer = threading.Timer(5.0, client.close)
timer.start()
try:
    client.rdma_get(key, region.window(offset, length))
finally:
    timer.cancel()
```

The waiting call raises `ClosingError`, and its region is closed. If the server's reply was already arriving, the call returns as usual instead and the region stays open.
Create a new client and register the memory again to continue.

## Shut down

Wait for every thread's transfer calls to return, then close each region, then the client:

```python
region.close()
client.close()
```

Closing a region while a transfer is using it raises `RdmaError`.
If a transfer is stuck, close the client to cancel it. The cancelled transfer closes its own region, so closing that region afterward does nothing.

Regions and clients also work as context managers:

```python
with GlideClient.create(config) as client:
    with client.register_rdma_region(bytearray(1 << 20)) as region:
        client.rdma_set(b"key", region.window(0, 4096))
```

A region that is never closed is freed when it is garbage-collected, with a `ResourceWarning`. Until then its pages stay pinned, so close regions explicitly.
