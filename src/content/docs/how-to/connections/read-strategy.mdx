import { Tabs, TabItem } from '@astrojs/starlight/components';

By default, Valkey GLIDE directs read commands to the primary node that owns a specific slot. For applications that prioritize read throughput and can tolerate possibly stale data, Valkey GLIDE provides the flexibility to route reads to replica nodes.

Valkey GLIDE provides support for the following read strategies, allowing you to choose the one that best fits your specific use case.

## Available Read Strategies

The table describes ordinary cluster reads. Candidate nodes belong to the key's shard; “local” means the client's configured availability zone (AZ). Writes continue to go to the primary. See [command routing](/concepts/client-features/command-routing/#read-strategy) for the standalone fallback difference.

| Strategy                                                                            | Description                                                                                                                                                                                                                                                 |
| ----------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Primary (Default)**                                                               | Always read from primary, in order to get the freshest data.                                                                                                                                                                                                |
| [All Nodes](#all-nodes)                                                             | Rotate reads across available primary and replica connections, without an AZ preference.                                                                                                                                                                    |
| [Prefer Replica](#prefer-replica)                                                   | Spread requests between all replicas in a round robin manner. If no replica is available, route the requests to the primary.                                                                                                                                |
| [AZ Affinity](#az-affinity)                                                         | Spread the read requests between replicas in the same client's availability zone in a round robin manner, falling back to other available replicas, then to the primary only if no replica is available.                                                    |
| [AZ Affinity Replicas and Primary](#az-affinity-replicas-and-primary-read-strategy) | Spread the read requests among nodes within the client's availability zone in a round robin manner, prioritizing local replicas, then the local primary, and falling back to other available replicas, then to the primary only if no replica is available. |
| [AZ Affinity All Nodes](#az-affinity-all-nodes)                                     | Spread the read requests equally among all nodes (primary and replicas) within the client's availability zone in a round robin manner, falling back to a round robin across all nodes if no node in the client's availability zone is available.            |

:::note[Replica reads]
Strategies that include replicas can return stale data. The `set`/`get` examples below demonstrate routing; a read from a replica is not guaranteed to observe the preceding write immediately.
:::

### All Nodes

Use All Nodes to share reads between the primary and replicas without preferring an AZ. This strategy is available in Java, Python, Node, and Go in 2.4.0 and later. It does not require a client AZ.

<Tabs syncKey="progLangInExamples">
  <TabItem label="Python">
    ```python
    from glide import (
        GlideClusterClient,
        GlideClusterClientConfiguration,
        NodeAddress,
        ReadFrom
    )

    addresses = [NodeAddress(host="address.example.com", port=6379)]
    client_config = GlideClusterClientConfiguration(addresses, read_from=ReadFrom.ALL_NODES)

    client = await GlideClusterClient.create(client_config)
    await client.set("key1", "val1")
    # get rotates across available primary and replicas for the key's shard
    await client.get("key1")
    ```
  </TabItem>

### AZ Affinity

When using the AZ Affinity read strategy, the `clientAz` setting is required to ensure that readonly commands are directed to replicas within the specified availability zone if they exist. Reads fall back to other available replicas, then to the primary only if no replica is available.

:::note[Configuring AZ strategies]
All AZ strategies require the application's AZ: `clientAZ` in Java, `clientAz` in Node, `client_az` in Python, or `WithClientAZ` in Go. The value must match the node AZ information reported by the server. An incorrect nonempty AZ can match no nodes and cause cross-AZ fallback. AZ strategies are incompatible with standalone `readOnly` mode.
:::

:::caution[Java AZ validation in 2.5.3-rc1]
Java 2.5.3-rc1 validates `clientAZ` for `AZ_AFFINITY`, `AZ_AFFINITY_REPLICAS_AND_PRIMARY`, and `AZ_AFFINITY_ALL_NODES`. A missing or empty value, including one that becomes empty after Java's `String.trim()`, causes `createClient` to throw `ConfigurationError` synchronously. Padded values such as `" us-east-1a "` are trimmed before use.

When upgrading, correct existing configurations that omit the AZ: they could previously fall back silently to `PreferReplica`. Padded values could fail to match the intended AZ. Python, Go, and Node already reject missing or empty AZ values for their supported AZ strategies; Java additionally normalizes surrounding whitespace.
:::

### AZ Affinity Replicas and Primary Read Strategy

When using the AZ Affinity Replicas and Primary read strategy, the `clientAz` setting is required to ensure that readonly commands are directed to replicas or the primary within the specified availability zone if they exist. Local replicas take priority over the local primary. In cluster mode, if neither is available, reads rotate across any available replicas and use the primary only when no replica is available. If the only available local node is the primary, it receives reads even when remote replicas are available.

In standalone mode, the final fallback instead rotates across all available primary and replica nodes. Local replicas still take priority over the local primary.

### AZ Affinity All Nodes

When using the AZ Affinity All Nodes read strategy, the `clientAz` setting is required to ensure that readonly commands are spread equally across all nodes (primary and replicas) within the specified availability zone if they exist. Unlike AZ Affinity Replicas and Primary, the local primary is an equal member of the rotation rather than a fallback, so it shares reads even when local replicas are available. If no local node is available, reads rotate across all available primary and replica nodes for the key's shard, including a remote primary even when remote replicas are available.

Compared with AZ Affinity Replicas and Primary in cluster mode:

* A local primary shares reads while local replicas are also available.
* If no local node is available, a remote primary shares reads with remote replicas.
* If the only available local node is the primary, both strategies use it; this case is unchanged.

Standalone clients use the same local-first, all-node rotation. However, including the primary in the final fallback pool is already the behavior of standalone AZ Affinity Replicas and Primary. See [command routing](/concepts/client-features/command-routing/#read-strategy) for the comparison.

:::note[Release availability]
AZ Affinity All Nodes is included in Java and Python (async and sync) in **2.5.3-rc1**. It is not available in their 2.5.0–2.5.2 releases. The examples below use the release candidate's API.
:::
