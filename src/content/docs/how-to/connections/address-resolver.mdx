GLIDE supports **custom address resolution**, allowing you to provide a callback that translates configured addresses to actual connection endpoints before connections are made. This is useful for custom DNS resolution, proxy address translation, and dynamic endpoint resolution in cloud environments.

## Use Cases

* **Custom DNS resolution** for service discovery systems
* **Address translation** for proxy or NAT setups
* **Dynamic endpoint resolution** for cloud environments (e.g., AWS ElastiCache behind NLBs)
* **Connecting through firewalls** where the server URL can't be resolved by default DNS

## Configuring

The address resolver is a callback that receives a `(host, port)` pair and returns the resolved `(host, port)` to use for the connection. It is invoked:

* During initial connection establishment for every configured address
* During cluster topology refreshes when new node addresses are discovered

## Fallback Behavior

The address resolver is designed to be fault-tolerant. If the resolver encounters an error, the client falls back to using the original address — the connection is never blocked by a misbehaving resolver.

Fallback occurs when:

* The resolver throws an exception or panics
* The resolver returns `null` or an invalid value
* The resolver returns an empty host or port 0 (Go)

This ensures that a faulty resolver does not prevent the client from connecting when the original address is valid.

## Important Considerations

* **Synchronous execution**: The resolver callback must be synchronous. Async resolvers are not supported.
* **Thread safety**: The resolver may be called from multiple threads concurrently. Ensure your implementation is thread-safe.
* **Performance**: The resolver is called during connection establishment and cluster topology refreshes. Avoid long-running operations that could delay connections.
* **Cluster mode**: In cluster mode, the resolver is also invoked for new node addresses discovered during topology refreshes, not just the initially configured addresses.
