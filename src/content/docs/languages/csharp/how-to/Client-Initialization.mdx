Valkey GLIDE provides support for both [Cluster](#cluster) and [Standalone](#standalone) configurations. Please refer to the relevant section based on your specific setup.

## Cluster

Valkey GLIDE supports [Cluster](https://valkey.io/topics/cluster-spec) deployments, where the database is partitioned across multiple primary shards, with each shard being represented by a primary node and zero or more replica nodes.

To initialize a [`GlideClusterClient`](https://github.com/valkey-io/valkey-glide-csharp/blob/main/sources/Valkey.Glide/GlideClusterClient.cs), you need to provide a [`ClusterClientConfiguration`](https://github.com/valkey-io/valkey-glide-csharp/blob/main/sources/Valkey.Glide/ConnectionConfiguration.cs) that includes the addresses of initial seed nodes. Valkey GLIDE automatically discovers the entire cluster topology, eliminating the necessity of explicitly listing all cluster nodes.

### Connecting to a Cluster

The `WithAddress` method accepts a host and port for a cluster node. The host can be either an IP address, a hostname, or a fully qualified domain name (FQDN).

### Example: Connecting to a cluster

```csharp
using Valkey.Glide;
using static Valkey.Glide.ConnectionConfiguration;

var config = new ClusterClientConfigurationBuilder()
    .WithAddress("address.example.com", 6379)
    .Build();

await using var client = await GlideClusterClient.CreateClient(config);
```

### Request Routing

In the cluster, data is divided into slots, and each primary node within the cluster is responsible for specific slots. Valkey GLIDE adheres to [Valkey OSS guidelines](https://valkey.io/topics/command-tips/#request-policy) when determining the node(s) to which a command should be sent in clustering mode.

For more details on the routing of specific commands, please refer to [the documentation within the code](https://github.com/valkey-io/valkey-glide-csharp/blob/main/sources/Valkey.Glide/Route.cs) for routing configuration.

### Response Aggregation

When requests are dispatched to multiple shards in a cluster (as discussed in the Request routing section), the client needs to aggregate the responses for a given command. Valkey GLIDE follows [Valkey OSS guidelines](https://valkey.io/topics/command-tips/#response-policy) for determining how to aggregate the responses from multiple shards within a cluster.

To learn more about response aggregation for specific commands, please refer to [the documentation within the code](https://github.com/valkey-io/valkey-glide-csharp/blob/main/sources/Valkey.Glide/ClusterValue.cs).

### Topology Updates

The cluster's topology can change over time. New nodes can be added or removed, and the primary node owning a specific slot may change. Valkey GLIDE is designed to automatically rediscover the topology whenever the server indicates a change in slot ownership. This ensures that the Valkey GLIDE client stays in sync with the cluster's topology.

## Standalone

Valkey GLIDE also supports Standalone deployments, where the database is hosted on a single primary node, optionally with replica nodes. To initialize a [`GlideClient`](https://github.com/valkey-io/valkey-glide-csharp/blob/main/sources/Valkey.Glide/GlideClient.cs) for a standalone setup, you should create a [`StandaloneClientConfiguration`](https://github.com/valkey-io/valkey-glide-csharp/blob/main/sources/Valkey.Glide/ConnectionConfiguration.cs) that includes the addresses of primary and all replica nodes.

### Example: Connecting to a standalone

```csharp
using Valkey.Glide;
using static Valkey.Glide.ConnectionConfiguration;

var config = new StandaloneClientConfigurationBuilder()
    .WithAddress("primary.example.com", 6379)
    .WithAddress("replica1.example.com", 6379)
    .WithAddress("replica2.example.com", 6379)
    .Build();

await using var client = await GlideClient.CreateClient(config);
```
