Client-side caching in Valkey GLIDE stores responses from cacheable read commands in a local in-memory cache on the client, reducing network round-trips and server load. When a cached command is issued again, the response is served directly from local memory without contacting the server.

<Aside type="caution" title="TTL-Only Caching (Default)">
  By default, client-side caching uses **TTL-based expiration only**. Cached entries may become stale before their TTL expires if **any client** modifies the underlying data, **including the same client that cached the value**. A read issued immediately after the same client's `SET` / `HSET` / `SADD` / `DEL` will still return the cached value until its TTL expires. Python, Java, Node.js, Go, and C# can opt into [server-assisted invalidation](#server-assisted-invalidation) through the [`CLIENT TRACKING`](https://valkey.io/commands/client-tracking/) protocol.
</Aside>

## How It Works

1. When a cacheable read command is executed, GLIDE first checks the local cache.
2. On a **cache miss**, the command is sent to the server, and the response is stored locally.
3. On a **cache hit**, the cached value is returned immediately without a network call.
4. Entries expire based on their configured TTL. Expiration is **lazy** — entries are removed when accessed after their TTL has elapsed, not proactively in the background.
5. When the cache reaches its memory limit, entries are evicted according to the configured eviction policy.

### Cached Commands

Only the following read commands are cached:

| Command      | Description                        |
| ------------ | ---------------------------------- |
| `GET`        | Retrieve a string value            |
| `MGET`       | Retrieve multiple string values    |
| `HGETALL`    | Retrieve all fields from a hash    |
| `SMEMBERS`   | Retrieve all members from a set    |

All other commands bypass the cache entirely. Write commands (`SET`, `HSET`, `SADD`, etc.) are never cached.

### `MGET` caching

GLIDE caches `MGET` per key rather than as a single response:

* **Full hit:** If every key is cached, GLIDE returns the values without contacting the server.
* **Partial hit:** GLIDE sends an `MGET` for only the missing keys, then merges the server values with the cached values in the original key order.
* **Storing results:** Each non-NIL value from the server is cached under its own key, so a later `GET` or `MGET` of that key can be served from the cache. NIL values are not cached.
* **Duplicate keys:** Duplicate keys keep their normal `MGET` semantics.
* **Metrics:** Each key counts as one cache hit or one cache miss.

:::caution[Partial hits are not atomic]
On the server, `MGET` reads all keys at a single point in time. On a partial hit, GLIDE combines cached values, which can be as old as the entry TTL, with values the server reads now, so the result is not a point-in-time snapshot of the keys. Use a client without a cache when you need a consistent read of several keys.
:::

### What Is Not Cached

* **NIL responses** — If a key does not exist, the `nil` response is not stored in the cache.
* **Entries larger than the cache** — If a single entry exceeds `maxCacheKb`, it is silently skipped.

## Configuration

To enable client-side caching, pass a `ClientSideCache` configuration when creating a client.

<ClientTabs>
  <ClientTab slot="python">
    ```python
    from glide import (
        GlideClient,
        GlideClientConfiguration,
        GlideClusterClient,
        GlideClusterClientConfiguration,
        ClientSideCache,
        EvictionPolicy,
        NodeAddress,
    )

    # Create a cache configuration
    cache = ClientSideCache.create(
        max_cache_kb=1024,         # 1 MB maximum cache size
        entry_ttl_ms=60_000,       # 60 second TTL per entry (0 = no expiration)
        eviction_policy=EvictionPolicy.LRU,  # LRU or LFU
        enable_metrics=True,       # Enable hit/miss tracking
    )

    # Standalone client
    config = GlideClientConfiguration(
        addresses=[NodeAddress("localhost", 6379)],
        client_side_cache=cache,
    )
    client = await GlideClient.create(config)

    # Cluster client
    cluster_config = GlideClusterClientConfiguration(
        addresses=[NodeAddress("localhost", 6379)],
        client_side_cache=cache,
    )
    cluster_client = await GlideClusterClient.create(cluster_config)
    ```
  </ClientTab>

    ```java
        .clientSideCache(cache)
        .build();

    // Cluster client
    GlideClusterClientConfiguration clusterConfig = GlideClusterClientConfiguration.builder()
        .address(NodeAddress.builder().host("localhost").port(6379).build())
        .clientSideCache(cache)
        .build();
    ```

### Configuration Options

| Option             | Type              | Default | Description                                                                                       |
| ------------------ | ----------------- | ------- | ------------------------------------------------------------------------------------------------- |
| `maxCacheKb`       | integer           | —       | Maximum cache size in kilobytes. Required.                                                        |
| `entryTtlMs`      | integer           | —       | Time-to-live per entry in milliseconds. Use `0` to disable TTL (entries persist until evicted).   |
| `evictionPolicy`   | `LRU` or `LFU`   | `LRU`   | Policy for removing entries when the cache is full.                                               |
| `enableMetrics`    | boolean           | `false` | When `true`, enables collection of hit/miss/eviction/expiration counters.                         |
| `serverAssisted` / `server_assisted` / `WithServerAssisted` | boolean | `false` | Enables server-assisted invalidation using Valkey's `CLIENT TRACKING ON BCAST` mode. Supported by Python, Java, Node.js, Go, and C#. Requires RESP3. |

## Eviction Policies

When the cache reaches its configured memory limit, it must remove entries to make room for new ones.

| Policy | Name                     | Behavior                                                                                                  |
| ------ | ------------------------ | --------------------------------------------------------------------------------------------------------- |
| `LRU`  | Least Recently Used      | Evicts the entry that has not been accessed for the longest time. Best for workloads with temporal locality. |
| `LFU`  | Least Frequently Used    | Evicts the entry with the lowest access count. Ties are broken by oldest access time. Best for workloads where popular items should stay cached. |

## Shared Cache

Multiple clients can share the same cache instance by passing the same `ClientSideCache` object to each client. This is useful when you want several connections to benefit from a single pool of cached data.

<ClientTabs>
  <ClientTab slot="python">
    ```python
    # Both clients share the same cache
    cache = ClientSideCache.create(max_cache_kb=1024, entry_ttl_ms=60_000)

    client1 = await GlideClient.create(
        GlideClientConfiguration(
            addresses=[NodeAddress("localhost", 6379)],
            client_side_cache=cache,
        )
    )
    client2 = await GlideClient.create(
        GlideClientConfiguration(
            addresses=[NodeAddress("localhost", 6379)],
            client_side_cache=cache,
        )
    )

    # client1 populates the cache
    await client1.set("key", "value")
    await client1.get("key")  # Cache miss — fetches from server

    # client2 gets a cache hit without contacting the server
    result = await client2.get("key")  # Cache hit
    ```

<Aside type="caution">
  When sharing a cache, keep in mind:

  * Clients connected to **different databases** should not share the same cache (keys may collide).
  * Clients using **different ACL users** with different permissions should not share the same cache.
  * Metrics (hit rate, miss rate, etc.) are shared across all clients using the same cache instance.
</Aside>

## Server-Assisted Invalidation

Python, Java, Node.js, Go, and C# support server-assisted invalidation for standalone and cluster clients. Enable the binding's server-assisted cache option. You do not need to call [`CLIENT TRACKING`](https://valkey.io/commands/client-tracking/) yourself because GLIDE issues `CLIENT TRACKING ON BCAST` during connection setup.

The server sends an invalidation message whenever a cached key changes. GLIDE then removes that entry from the local cache, so the next read fetches the current value.

### Enabling server-assisted mode

Create the cache as shown below, then attach it to a standalone or cluster client configuration as in [Configuration](#configuration).

<ClientTabs>
  <ClientTab slot="java">

    ```java
        .maxCacheKb(1024)
        .entryTtlMs(60_000)
        .serverAssisted(true)
        .build();
    ```
  </ClientTab>

  <ClientTab slot="python">

    ```python
        max_cache_kb=1024,
        entry_ttl_ms=60_000,
        server_assisted=True,

    ```
  </ClientTab>

  <ClientTab slot="node">

<Aside type="caution" title="RESP3 Required">

## Limitations

| Limitation | Details |
| --- | --- |
| **TTL-only expiration** | No server-side invalidation by default. Cached values may become stale if the key is modified on the server before the TTL expires. Python, Java, Node.js, Go, and C# support [server-assisted invalidation](#server-assisted-invalidation). |
| **Lazy expiration** | Expired entries are cleaned up on access, not proactively in the background. |
| **Limited command coverage** | Only `GET`, `MGET`, `HGETALL`, and `SMEMBERS` are cached. Other read commands are not cached. |
| **`MGET` not atomic on partial hits** | A partially cached `MGET` combines cached and server values, so the result is not a point-in-time snapshot. See [`MGET` caching](#mget-caching). |
| **NIL not cached** | If a key does not exist, the nil response is not stored. |
| **No invalidation on writes** | In TTL-only mode, writing to a key such as `SET`, `HSET`, `SADD`, or `DEL` does not invalidate the local cache entry, even when the same client issues the write. Subsequent reads return the stale value until its TTL expires or memory pressure evicts it. In [server-assisted mode](#server-assisted-invalidation), the server sends invalidation messages that clear stale entries. |

### Compatibility with managed services

Server-assisted invalidation requires the deployment to expose the `CLIENT TRACKING` command. The table below summarizes compatibility:

| Deployment                                                          | Exposes `CLIENT TRACKING`? | Notes                                                                                                                                                                                                                                                       |
| ------------------------------------------------------------------- | -------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Self-managed Valkey or Redis OSS                                    | ✅ Yes                     | Requires Valkey 7.2+ / Redis OSS 6.0+ (any version that supports `CLIENT TRACKING`).                                                                                                                                                                        |
| Amazon MemoryDB                                                     | ✅ Yes                     | Standard `CLIENT` surface available.                                                                                                                                                                                                                        |
| Amazon ElastiCache (cluster-mode replication group, non-serverless) | ✅ Yes                     | Standard `CLIENT` surface available.                                                                                                                                                                                                                        |
| Amazon ElastiCache **Serverless**                                   | ❌ No                      | Only `CLIENT GETNAME / SETNAME / REPLY / HELP` are exposed; `CLIENT TRACKING` returns `ERR unknown subcommand 'tracking'`. Client-side caching remains TTL-only on Serverless. |

If your deployment is in the last row, plan around the TTL-only model: cache only data that is immutable or can tolerate staleness up to its TTL.

## Validating cache behavior

The metrics counters show whether requests hit the cache. The following sequence assumes the default TTL-only mode with `serverAssisted` disabled:

| Step | Operation           | What you should see                                                                                                                                       |
| ---- | ------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1    | `SET k v1`          | Server-only. Cache state unchanged.                                                                                                                       |
| 2    | `GET k`             | Cache **miss**, populates the entry. `entryCount=1`, `totalLookups=1`, `hitRate≈0`.                                                                       |
| 3    | `GET k`             | Cache **hit**. `totalLookups=2`, `hitRate≈0.5`.                                                                                                           |
| 4    | `GET nonexistent`   | Cache miss; the `nil` reply is **not** cached. `entryCount` stays at `1`, `missRate` rises.                                                               |
| 5    | `SET k v2`          | Server-only. **The cache still holds `v1`** because TTL-only mode does not invalidate it.                                                               |
| 6    | `GET k`             | Returns the stale value `v1`. The cache catches up only after the entry's TTL expires or memory pressure evicts it.                                     |

### Confirming TTL-only behavior on the same client

With server-assisted caching disabled, the cache does **not** clear after the same client writes a key it had cached. You can confirm this with four operations:

1. `SET k "before"`
2. `GET k` (populates the cache).
3. `SET k "after"` (writes go through to the server; the cache is untouched).
4. `GET k` → returns `"before"` until the entry's TTL expires.

This is the expected TTL-only behavior. Python, Java, Node.js, Go, and C# applications can enable [server-assisted invalidation](#server-assisted-invalidation) when the deployment supports `CLIENT TRACKING`. Otherwise, cache only values that can remain stale until their TTL expires.

## Best Practices

* **Set an appropriate TTL** — Choose a TTL that balances freshness with cache effectiveness. Shorter TTLs reduce staleness risk; longer TTLs improve hit rates.
* **Size the cache appropriately** — Monitor eviction counts. High eviction rates indicate the cache is too small for the working set.
* **Use metrics to tune** — Enable metrics during development and load testing to understand cache behavior and optimize configuration.
* **Use TTL-only mode for read-heavy, slow-changing data.** Without server-assisted invalidation, restrict the cache to values that can tolerate staleness up to the configured TTL. Avoid caching keys that the application writes during the cache lifetime.
* **Avoid sharing caches across databases** — Keys in different databases may have the same name but different values.
